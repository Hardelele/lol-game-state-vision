# Индекс роликов YouTube для набора (#843)

Код: `tools/video_index.py` (командная строка, SQLite, лист проверки),
`lolstream/youtube_preview.py` (сеть: список канала, сведения, раскадровка,
точечные кадры HLS), `lolvision/video_verdict.py` (лента, моменты кадров,
итог — без сети и моделей), `lolvision/hud_champion.py` (свой чемпион по
иконкам умений), `lolvision/video_meta.py` (заявки названия: ранг, роль,
чемпионы), `lolvision/patch_calendar.py` (календарь патчей 2026). Тесты —
`tests/test_video_index.py` (без сети: сохранённые ответы моделей по шести
настоящим роликам в `tests/fixtures/video_index/verdicts.json`, кадров нет).

Задача: по ролику за секунды, не скачивая его, сказать, годится ли он для
набора модели решений (полная игра, вид игрока или наблюдателя, свой
чемпион и роль, ранг-заявка, патч, видна ли миникарта), и пройти так целые
каналы за сезон.

## Команды

```
python tools/video_index.py assets                                  # иконки Data Dragon, один раз
python tools/video_index.py channel @ProTopArchive --since season   # канал за сезон
python tools/video_index.py channel @X --tab streams --since patch  # вкладка трансляций, текущий патч
python tools/video_index.py search "Volibear top challenger" --n 40 --since season
python tools/video_index.py video 6k5-vQ_GQ_M --force               # один ролик заново
python tools/video_index.py show --champion Volibear --role top --usable
python tools/video_index.py show --usable --view player --minimap --max-cut 60 --json
python tools/video_index.py reverdict                               # итог заново по фактам, без сети
```

`--since`: `patch` (с выхода текущего патча), `season` (с 26.01), номер
патча (`26.18`), дата (`2026-09-01`) или `all`. Повторный проход берёт только
ролики, которых в индексе нет или чья строка — ошибка (`--force` — все).

Где что лежит (вне git):

* `D:\bc-data\index\videos.sqlite` — индекс, таблица `videos`, одна строка на ролик;
* `D:\bc-data\previews\<id>\` — кадры предпросмотра (`t<секунда>.jpg`, 1280 px),
  полоса раскадровки, `sheet.jpg` (лист для проверки глазами: кадры с подписями
  моделей и итог), `facts.json` (строка индекса целиком);
* `D:\bc-data\index\ddragon\16.20.1\` — иконки чемпионов и умений Data Dragon;
* модели — `runs/` основного каталога (`--runs`); в рабочей копии их нет.

Процесс бережёт машину и сеть (они общие с игрой владельца):

* приоритет «ниже обычного» (его наследуют yt-dlp и ffmpeg), 2 потока
  BLAS/OpenCV/torch, модели — на cuda;
* один ролик за раз (`--workers 1`, не больше 2), одна загрузка за раз внутри
  ролика, пауза 2 с между роликами;
* общий предел загрузки на процесс — `--max-rate 2` МБ/с (ведро токенов на
  все потоки), yt-dlp — `--limit-rate 2M`; вызовы yt-dlp — по одному с
  паузой 2 с;
* ролики длиннее `--max-hours 3` — стрим целиком: не разбираются (`long`).

Почему так (2026-10-15): два прохода по 2–4 ролика сразу заняли ~98% ЦП;
4 параллельные загрузки кадров и 8 листов раскадровки разом совпали с
вылетом владельца из онлайн-игры; ролик-стрим на 23.7 ч стоил 83 МБ и 11 мин
одной раскадровкой. С пределом 2 МБ/с замер сети за 60 с — пик 1.8 МБ/с,
среднее 0.34 МБ/с; ЦП процесса — единицы процентов.

## Как работает предпросмотр

1. **Список** — `yt-dlp --flat-playlist -J` с
   `youtubetab:approximate_date`: id, название, длина и грубая дата
   («2 weeks ago» → метка; ~2 с на 30–400 роликов). Шорты, ролики короче 8 мин
   и старше `--since` (с запасом 10 дней на грубость даты) отсекаются без
   запросов к ролику.
2. **Сведения** — `yt-dlp -J --skip-download` (медиана 2.7 с): точная дата,
   описание, форматы. Опубликован раньше `--since` — строка `old`, дальше не
   смотрим.
3. **Раскадровка** (`sb0`, листы 3×3 кадров 320×180, кадр раз в ~10 с у
   ролика 25 мин; ~1 МБ, медиана 3.8 с на все листы) → тип сцены каждого кадра
   (`SceneNet`, вход 256×144 — меньше кадра раскадровки; 0.2 с на ролик) →
   отрезки игры (`timeline`: game / tab / shop; разрыв — не-игра дольше 45 с).
4. **Моменты** (`pick_times`): у каждого отрезка игры не короче 4 мин —
   100 / 190 / 300 / 430 с от начала отрезка (роль видна в первые минуты),
   потом 35 / 55 / 75 / 92% отрезка; всего до 10 (по умолчанию 8).
5. **Точечные кадры 1080p** — из HLS-потока ролика (`m3u8_native`, avc):
   плейлист — сегменты по ~6 с, сегмент начинается с ключевого кадра. Читаем
   первые ~0.45 МБ сегмента, обрываем соединение, ffmpeg распаковывает первый
   кадр из трубы; не распаковался чисто — дочитываем по 0.3 МБ. Кадр — момент
   начала сегмента (до 6 с раньше запрошенного).
6. **Модели по кадру** (`analyze_frame`): тип сцены; раскладка HUD
   (портреты наблюдателя — `roster` + `spectator_hud`; полоса здоровья своей
   панели — `player_hud`, панель умений — `hud_spells.locate_panel`, полоса
   статистики — `hud_stats`); часы матча с полосы статистики вида игрока;
   миникарта (`minimap_locate.Locator.locate` — найдена ли, масштаб,
   совпадение); рамка камеры на миникарте → мировые координаты → зона
   (`rift.zone`); свой чемпион по иконкам Q/W/E/R (вид игрока).
7. **Итог** (`video_verdict.verdict`) — ниже.

Замеры (этот прогон, 2026-10-15, ролики без сетевых ошибок):

| Что | Медиана | Разброс |
| --- | --- | --- |
| сведения `yt-dlp -J` | 2.7 с | 2.4–9.6 с |
| раскадровка (все листы) | 3.8 с | 1.7–17 с |
| 8 точечных кадров (4 загрузки сразу) | 4.6 с | 3.5–27 с |
| один кадр | 1.8 с | 1.1–24 с |
| модели на 8 кадров | 2.3 с | 1.8–118 с (сбой GPU-очереди у соседей) |
| весь ролик | 16.6 с | — |
| трафик на ролик | 4.9 МБ | 4.4–9.3 МБ |

Для сравнения: целый сегмент HLS — 2.3–3.2 МБ и ~3 с, весь ролик 1080p60 25
мин — ~680 МБ. Прямой адрес потока (`videoplayback`, DASH) с `ffmpeg -ss`
YouTube душит: за 90 с ни одного кадра (то же в `lolstream/video_stream.py`).
Range в адресах сегментов HLS сервер не соблюдает (200 и всё тело), поэтому
чтение обрывает клиент.

Адрес потока подписан и живёт ~6 ч (`expire` в адресе): `HlsStream` проверяет
срок перед кадром, истёкший — `ExpiredError`, и ролик берётся заново со
сведений.

YouTube ограничивает частоту: при 4 параллельных `-J` на втором десятке
роликов — «Sign in to confirm you're not a bot» (3 из 24). Поэтому вызовы
yt-dlp идут по одному с паузой 2 с, временные сбои (бот-проверка, обрыв
прокси, сброс соединения) повторяются через 20 / 60 / 180 с, а после
бот-проверки проход ждёт 5 мин. Ролик, у которого больше половины кадров не
получено, — строка-ошибка; следующий проход разберёт его заново.

### Годится ли раскадровка сама по себе

Проверено на 4 роликах (2 вида игрока, 2 наблюдателя), по 20 игровых кадров
раскадровки, увеличенных до 1920×1080:

| Признак | Вид игрока | Наблюдатель |
| --- | --- | --- |
| тип сцены «игра» | да (отрезки игры совпадают с точечными кадрами) | да |
| полоса здоровья своей панели (`player_hud`) | 5 / 20 и 10 / 20 | 0 / 20 и 0 / 20 |
| панель умений найдена | 1 / 20 и 4 / 20 | 0 |
| портреты наблюдателя | — | 0 / 20 (портреты 4–6 px) |
| часы матча | 0 | 0 |

Итог: раскадровка годится для ленты «игра / не игра» и длины игровой части
(шаг ~10 с), даёт слабый положительный признак вида игрока и ничего — для
наблюдателя, часов, чемпиона. Поэтому вид, часы и чемпион — только по
точечным кадрам 1080p.

## Что определяется

| Поле | Как | Ограничения |
| --- | --- | --- |
| `patch` | название / описание («Patch 26.20», «16.20» клиента) или по дате публикации (`patch_source` = title / description / upload) | по дате — верхняя граница: перезалив позже игры |
| `view` | голоса кадров: портреты наблюдателя — spectator; полоса своей панели, найденная панель умений или прочитанные часы — player; ≥ 2 голосов и ≥ 70% — решено, иначе unknown | |
| `champion` | вид игрока — иконки умений Q/W/E/R против Data Dragon (`hud_champion`): средняя оценка ≥ 0.40 и отрыв ≥ 0.08; иначе — заявка (`champion_source` = hud / claim / hud≠claim) | наблюдатель — только заявка (портрет в HUD наблюдателя — облик, иконки DD — базовый облик) |
| `role` | зона камеры на миникарте в 80–600 с матча: линия ≥ 60% — top / mid / bot, лес и река ≥ 60% — jungle; бот делится на bot / support заявкой или тегом Support в Data Dragon; нет камеры — заявка | камера стримера не всегда на своём чемпионе; миникарта под вебкой — роли по камере нет |
| `games` | часы HUD: сброс часов — следующая игра, у каждой — начало в ролике, длина, вырезано секунд, полная ли, чемпион | только вид игрока: часы наблюдателя (сверху по центру) не читаются |
| `full_game` | игра видна с начала (матч начался не раньше чем за 90 с до начала её участка) и до конца (≥ 14 мин), вырезано ≤ 40% матча между кадрами; без часов — отрезок раскадровки ≥ 14 мин | конец игры по часам не проверяется: длина = последнее прочтение + остаток отрезка |
| `cut_s`, `cuts` | сколько секунд матча нет в ролике: часы между кадрами ушли дальше ролика больше чем на 8 с | вырез меньше 8 с не виден; кадры редкие — места вырезов неточны |
| `minimap_share`, `minimap_scale` | доля игровых кадров с найденной миникартой, медиана масштаба | < 50% — «закрыта вебкой/оверлеем или не на месте» (заметка) |
| `hud_share` | доля кадров вида игрока с панелью умений | |
| `rank_claim`, `role_claim`, `champion_claim` | слова названия и описания (Challenger / GM / Master / Rank 1, кор. и кит. тоже; «Champions in this video: X», первый в «X vs Y») | заявка автора, не проверяется |
| `usable` | полная игра, вид решён, чемпион известен, название — не нарезка/гайд/шорт | вырезы и миникарта — не причина отказа, а поля для отбора (`--max-cut`, `--minimap`) |
| `confidence` | среднее трёх: доля голосов за вид; чемпион (hud — 0.5 + 5 × отрыв, заявка 0.6, расходятся 0.4); полнота (1 − доля вырезанного, без часов 0.7) | шкала согласия, не вероятность |

### Склейки и несколько игр

Архивы стримов (сеть ProTopArchive / Pro ADC Archive) вырезают время
смерти и ожидания: у Kingen `_508S98our4` часы между кадрами 597 → 655 с
ролика шли вровень (799 → 857 с матча), а на следующих 40 с ролика матч
ушёл на 83 с. Игра от начала до конца — полная, вырезанное — `cut_s`
(здесь 277 с в 6 местах). Ролики с комментарием (Nemesis) режут так же
(~300 с из 1200). «Нарезка» — когда вырезано больше 40% матча между кадрами.

Те же архивы клеят 2–3 игры подряд без загрузки — раскадровка видит один
отрезок, а часы сбрасываются (`BA7OqRG-QVE`, «Varus · Renekton · Jayce»:
1546 с матча на 1497 с ролика, 756 с — на 2346 с, 541 — на 3201 с). Сброс
часов — новая игра, если следующее прочтение согласно с новым, а не с
прежним (иначе это ошибка чтения). Чемпион — по кадрам этой игры, а если
игр столько же, сколько чемпионов в названии, — и заявка по порядку.
Кадров на игру при 8 на ролик мало (3 — на вторую и третью): их чемпион по
HUD часто не решается.

## Ограничения

* Наблюдатель: часов нет — полнота только по раскадровке, склейки не видны;
  свой чемпион — только заявка.
* Роль по камере неверна, если стример держит камеру не на себе; миникарта
  у части стримеров закрыта вебкой (ProTopArchive — у большинства) — тогда
  роль из названия.
* Конец игры не проверяется по экрану победы/поражения: обрыв трансляции в
  середине игры длиннее 14 мин будет «полной».
* Патч по дате публикации — верхняя граница; календарь 2025 не внесён
  (ролики до 26.01 — патч неизвестен).
* yt-dlp без JS-рантайма (deno не установлен) предупреждает, что часть
  форматов может пропасть; HLS 1080p avc был у всех разобранных роликов.
* Частота запросов к YouTube и полоса ограничены: скорость прохода — ~2 ролика в
  минуту в один поток при 2 МБ/с (без пределов было ~4).
