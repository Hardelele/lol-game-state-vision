# Вторая модель: юниты на основном виде (план, #755)

Цель — по основному виду (без HUD и миникарты на входе) получать для каждого
кадра список юнитов: чемпионы (кто, чья команда), миньоны, монстры,
строения, варды; их ХП, ресурс (ману), уровень; положение на экране и на
карте. И связать это с первой моделью (камера по кадру) в одно «состояние
игры» на кадр.

Документ — план, кода нет. Числа без ссылки на замер — оценки, они помечены.
Проверено 2026-10-10: репозитории через GitHub API, датасеты через API
HuggingFace, кадры `dataset/videos/` и `data/replay/rand300` (патч 16.20) —
разовыми скриптами, которые в репозиторий не идут.

## Коротко

1. **Готовых данных для основного вида нет.** Почти всё в индексе — миникарта
   или таблицы. Из основного вида — LeagueAI (5 классов, веса и датасет так и
   не выложены), пара цветовых детекторов полосок ХП и мелкие наборы Roboflow
   (десятки–сотни кадров, старые патчи). Позиции из реплеев (maknee, TLoL,
   ROFL) — патчи 11–15, без кадров; нынешние `.rofl` не декодирует никто:
   пакеты обфусцированы, а обфускация меняется каждый патч.
2. **Своя разметка дешёвая, и источника у неё два.**
   * **Replay API** (`/replay/render`): на паузе снимается один и тот же кадр
     с юнитами и без них, с полосками и без, с HUD и без. Разность кадров —
     точные маски юнитов и полосок, камера известна точно. Ограничение «только
     свои реплеи» не подтвердилось: клиент скачивает `.rofl` любого матча
     текущего патча своего региона по gameId
     (`/lol-replays/v1/rofls/{gameId}/download/graceful`, так делает pyLoL).
   * **Сами ролики YouTube.** Над каждым чемпионом канал рисует **имя
     чемпиона**, уровень, ХП и ресурс (проверено на `58w57eJ5Qks`, 05:10).
     HUD того же кадра (на входе модели закрыт маской) показывает ХП, ресурс и
     уровень всех десяти, миникарта — их положение. То же «бесплатное
     учение по замаскированному HUD», что дало метки камере.
3. **Модель — этапами, а не одна сеть «на всё».** Детектор без якорей
   (точки и рамки, масштаб юнитов почти постоянный) на кадре 960×544 →
   кропы в полном разрешении → маленькие головы: чтение полоски (ХП, ресурс,
   уровень, команда, щит), имя над полоской, облик чемпиона (выбор среди
   десяти в составе матча, а не среди ~172). Оценка: 10–15 мс на кадр 1080p
   на RTX 5060 Ti вместе с моделью камеры — запас для реального времени есть.
4. **С моделью камеры — раздельные энкодеры, общий конвейер и общий формат
   состояния.** Модель камеры работает на виде сверху 6 ед./px — полоски и
   текст там пропадают. Экран → карта — через камеру (модель 1) и точную
   геометрию камеры из Replay API. Замер на кадрах Replay API подтвердил
   ошибку масштаба `projection.json` из #753 (0.94 и 0.86 против 0.906 и
   0.847), её надо заменить точной проекцией.
5. **Первый шаг требует от пользователя ~1 часа:** открыть реплей, чтобы
   проверить, что именно выключает каждый флаг рендера, стоит ли кадр на
   паузе неподвижно и даёт ли привязка камеры к юниту его координаты.

### 1.3. Чего нет нигде

* Открытого датасета основного вида LoL с рамками чемпионов и их именами,
  с ХП/ресурсом/уровнем, с вардами, монстрами, строениями. Ни на текущем
  патче, ни на старых (кроме 5 классов LeagueAI, которые не выложены).
* Классификатора чемпионов по 3D-модели в игре и тем более по скинам
  (~172 чемпиона, по оценке 1800+ скинов). Есть только классификаторы иконок.
* Декодера пакетов текущего патча (позиции всех юнитов из `.rofl`).
* Пар «кадр видео ↔ точные позиции юнитов».

Значит, разметку делаем сами. Хорошая новость — её можно получать почти без
ручного труда (раздел 2).

## 2. Своя разметка

### 2.1. Что видно на кадре канала (проверено на `58w57eJ5Qks_t00300.jpg`)

* Над каждым чемпионом — **имя чемпиона** (не ник: «Volibear», «Irelia»,
  «Hecarim»), под ним плашка: квадрат уровня слева (~20 px), полоска ХП
  ~95×11 px с засечками, под ней ресурс ~3 px; всего ~118 px в ширину при
  1080p (у spectral-sight — 117 px). Цвет ХП — команда (синяя/красная);
  у миньонов — тонкие полоски ~52 px без имени и уровня.
* Чемпион ~150 px в высоту, миньон 40–60 px, вард ~20–30 px (оценка по
  кадру). В сцене модели камеры (720 px по ширине вместо 1315) — вдвое
  меньше: полоски там 2–5 px, текст нечитаем.
* Левая и правая панели HUD — портрет, уровень, ХП, ресурс всех десяти;
  внизу — табло с чемпионами, предметами, KDA; миникарта — позиции.
  На входе модели всё это закрыто маской `spectator-volibear-challenger`.

Засечки на полоске ХП — каждые 100 ХП (крупные через 1000), поэтому шаг
засечек даёт максимум ХП, а доля заливки — текущий: ХП можно получить в
единицах, а не только долей. Проверить на кадрах с известным ХП (Live Client
Data/HUD).

### 2.2. Путь A: Replay API — разность рендеров (основной источник точной разметки)

Флаги `/replay/render`, которые клиент 16.20 отдаёт (из
`data/replay/rand300/game.json`): `champions`, `characters`, `minions`,
`environment`, `particles`, `fogOfWar`, `floatingText`, `healthBarChampions`,
`healthBarMinions`, `healthBarPets`, `healthBarStructures`, `healthBarWards`,
`interfaceAll` (и по частям), `outlineSelect`, `outlineHover`,
`selectionName`, `cameraAttached`, `cameraMode`, `fieldOfView`,
`cameraPosition`/`cameraRotation`.

Схема для одного момента (игра на паузе, камера поставлена `blend: snap`):

| Снимок | Флаги | Что даёт |
|---|---|---|
| `full` | всё как в роликах | **вход модели** |
| `clean` | `interfaceAll=false` | тот же кадр без HUD — для аугментаций «другой HUD» |
| `noBars` | все `healthBar*=false`, `floatingText=false` | `full − noBars` = точные пиксели всех плашек: рамки, имя, доля заливки ХП/ресурса, цифра уровня |
| `noChamp` | `champions=false`, `particles=false` | `noBars − noChamp` = маска видимой части чемпионов |
| `noMinion` | `minions=false` | маска миньонов |
| `noChar` | `characters=false` | остаток после чемпионов и миньонов — монстры, варды, питомцы (что именно — проверить, шаг 0) |
| `noFog` | `fogOfWar=false` | что скрыто туманом (для меток «есть, но не виден» — по желанию) |

Метки:

* **Экземпляры.** Маска чемпионов — объединение. Делится на экземпляры по
  плашкам (у каждого чемпиона ровно одна, её прямоугольник чёткий) и по
  позициям чемпионов, если их можно снять (ниже).
* **ХП/ресурс/уровень** читаются классическим CV по чистой плашке из
  `full − noBars`: рамка известна, заливка против тёмного фона, ошибка ~1 px
  из ~95 (≈1%). Плашки, наложенные друг на друга, помечаются как
  «перекрыта» и не дают ХП-метку.
* **Строения** стоят на постоянных местах карты, **лагеря монстров** —
  тоже: тип строения/монстра получается проекцией известных координат
  (таблица на патч) в экран точной камерой. Рамка — по маске.
* **Тип миньона** (ближний/дальний/осадный/супер) и **тип варда** — по
  размеру маски и ширине плашки, затем кластеризация и ручная проверка
  нескольких сотен кропов (часы, не дни).
* **Чемпион и скин:** состав матча (имя, команда, уровень, предметы,
  `skinID`) — Live Client Data API (`/liveclientdata/playerlist`). Работает
  ли он при просмотре реплея и отдаёт ли `skinID` — проверить (шаг 0).
  Запасной путь — метаданные `.rofl` (у ROFL поле `skin` = имя чемпиона) и
  match-v5. Имя над плашкой в реплее можно включить так же, как у канала.
* **Позиция на карте.** Гипотеза для шага 0: `selectionName=<юнит>` +
  `cameraAttached=true` — камера следует за юнитом, и `cameraPosition` даёт
  его координаты. Тогда на каждый момент 10 запросов дают позиции всех
  чемпионов точно. Если не выйдет — точка основания маски (центр нижней
  кромки / тень) проецируется на землю точной камерой; ошибку даёт высота
  рельефа (раздел 4.2).

Почему разность, а не синтетика: модель видит настоящую сцену с настоящими
перекрытиями, эффектами и скинами; метка считается по упрощённым рендерам
того же момента, а вход — полный рендер. Синтетику оставляем как
аугментацию (вставка кропов чемпионов из масок в чужие сцены — копи-пейст,
как LeagueAI, но из реальных масок).

**Как получать реплеи.** LCU (клиент, порт и токен из `lockfile`):
список апекс-лиги (`/lol-ranked/v1/apex-leagues/RANKED_SOLO_5x5/CHALLENGER`),
история матчей игрока (`/lol-match-history/v1/products/lol/{puuid}/matches`),
скачивание `/lol-replays/v1/rofls/{gameId}/download/graceful`. Ключ Riot API
не нужен (pyLoL использует match-v5, но LCU даёт то же для своего региона).
Для редких чемпионов — искать игры их «мейнеров» через историю матчей.

**Трудозатраты (оценка).** Инструмент (`tools/replay_entities.py` поверх
`replay_capture.py`): 3–5 дней. Сбор: 6–7 снимков на точку, по замеру шага 0
— ориентир 1.5–2 с на точку, т. е. ~2000 точек в час; 20 игр × 300 точек ≈
3 часа работы ПК без участия человека. Объём: ~1 ГБ на 2000 точек (JPEG
полного кадра + PNG-маски).

**Риски и ограничения.**

| Риск | Чем грозит | Что делать |
|---|---|---|
| Пауза не замораживает всё (вода, трава, анимации простоя) | шум в разности | шаг 0: два одинаковых снимка подряд → карта шума; порог; при необходимости морфология |
| Флаг выключает не то, что ожидается (`characters` и башни, варды и `minions`) | неверные классы | шаг 0: таблица «флаг → что пропало» по снимкам |
| Только текущий патч, реплей живёт ~2 недели | данные устаревают по графике (новые чемпионы, скины, эффекты) | собирать понемногу каждый патч; модель учить на смеси патчей |
| Свои настройки графики ≠ настройки канала | сдвиг домена | одинаковое разрешение и качество, имена чемпионов над плашками; проверять ширину плашки 117–118 px |
| Окно игры должно быть на переднем плане (`ImageGrab`) | ПК занят на время сбора | позже — Windows Graphics Capture (снимает и перекрытое окно) |
| Распределение камеры | случайная камера смотрит в пустой лес (см. replay-api.md) | ставить камеру у чемпионов и волн, со случайным сдвигом |
| Регион/аккаунт | скачиваются только матчи своего региона | для наших целей не важно |

### 2.3. Путь B: сами ролики — «HUD как учитель»

На кадре канала уже есть всё для слабой разметки видимых чемпионов:

* имя над плашкой → **кто это** (закрытый словарь ~172 имени, один шрифт —
  хватает классификатора кропа текста или шаблонов, OCR общего вида не
  нужен);
* цвет ХП → **команда**; цифра → **уровень**; доля заливки → **ХП**;
* боковые панели HUD → ХП, ресурс, уровень всех десяти: сверка по имени
  (портрет ↔ имя) даёт проверку чтения плашки на тысячах кадров;
* миникарта → положение каждого чемпиона на карте (детектор иконок; иконки
  всегда базовые, без скинов — по spectral-sight).

Отсюда главное: **облик чемпиона под плашкой получает метку бесплатно**,
включая скины, которые реально играют в high elo. Кроп под плашкой → имя
чемпиона: на одном ролике это тысячи примеров. Когда плашка закрыта или
вне кадра (чемпион у верхнего края), работает классификатор облика,
обученный на этих метках.

Трудозатраты: классический читатель плашек (цвет + геометрия + шаблоны
цифр/имён) — 2–3 дня; он же базовая точка и источник псевдо-меток.
Ограничения: метки — только для того, что нарисовано (чемпионы с плашкой);
миньоны и варды без имён; позиции на карте с точностью миникарты
(~58 ед./px, см. replay-api.md); канал один (у другого канала над плашкой
может быть ник, у вида игрока — тоже ник, своя плашка зелёная).

### 2.4. Путь C: декодированные реплеи + камера

Идея из индекса — позиции юнитов из реплея + точная камера → проекция в
экран — **на текущем патче недоступна**: декодера пакетов нет (1.2).
Датасеты maknee (12.10–13.2) связать с картинкой нельзя. Если декодер
появится (или привязка камеры к юниту из шага 0 даст позиции чемпионов), путь
сводится к A. Отдельной работы не планируем.

### 2.5. Путь D: синтетика (как LeagueAI)

3D-модели и скины можно взять из файлов клиента (через сторонние
экстракторы WAD) или из model viewer, отрисовать с анимациями и наложить на
сцены. Плюс — любой чемпион и скин. Минусы — эффекты, освещение, плашки и
перекрытия придётся моделировать; 1–2 недели работы; сдвиг домена.
**Не нужен для MVP**: путь A даёт реальные маски, путь B — реальные скины.
Возвращаться, если не хватит редких чемпионов/скинов (начать с копи-пейста
реальных масок из пути A).

### 2.6. Сравнение

| Путь | Что даёт | Точность меток | Ручной труд | Срок | Главный риск |
|---|---|---|---|---|---|
| A. Replay API | маски, рамки, ХП/ресурс/уровень, строения, монстры, варды, состав, (позиции) | пиксельная | часы (типы миньонов/вардов) | 1–1.5 нед. | что флаги ведут себя не так (шаг 0) |
| B. HUD роликов | имя, команда, уровень, ХП видимых чемпионов; облик со скинами; позиции с миникарты | хорошая для плашек, грубая для позиций | нет | 3–5 дней | один канал |
| C. Пакеты + камера | позиции всех юнитов | точная | — | — | нет декодера |
| D. Синтетика | любой чемпион/скин | точная, но домен другой | нет | 1–2 нед. | сдвиг домена |

Рекомендация: A + B вместе. A — эталон и всё, кроме скинов; B — облик и
перенос на настоящие ролики, проверка на целевом домене.

## 3. Постановка задачи и архитектура

### 3.1. Что выдаёт модель на кадр

Для каждого юнита: класс (чемпион / миньон×4 / монстр×~15 / башня /
ингибитор / нексус / вард×~5 / питомец-клон / прочее), команда, рамка тела,
точка основания (на земле), рамка плашки, ХП (доля, при засечках — единицы),
ресурс (доля и тип по цвету: мана/энергия/ярость/нет), уровень (1–18,
только чемпионы), щит (есть/доля), для чемпиона — имя (среди состава матча)
и вероятность.

### 3.2. Варианты

| Вариант | Плюсы | Минусы |
|---|---|---|
| Один детектор с головами «всё сразу» (YOLO/DETR + головы ХП, имени) | одна сеть | 172 класса облика в детекторе учатся плохо на редких; ХП с точностью 1% требует полного разрешения, а детектор работает на уменьшенном |
| **Этапы: детектор → кропы в полном разрешении → головы** | каждая часть проста и проверяема; головы получают пиксели плашки 1:1; имя и облик учатся на своих данных | два прохода, сложнее конвейер |
| Классическое CV (как spectral-sight) | без обучения | ломается на перекрытиях, эффектах, щитах; нет облика |

**Рекомендация — этапы.**

1. **Детектор** на кадре 960×544 (маска HUD как у модели камеры, но для
   полной картины лучше учить на `clean` + случайный HUD, чтобы маска не
   была обязательна). Без якорей, в духе CenterNet: тепловые карты центров
   плашек и точек основания тел по классам, регрессия размеров. Масштаб
   юнитов в спектаторе почти постоянный (зум фиксирован), поэтому сложная
   пирамида признаков не нужна; NMS не нужен. Базовая точка для сравнения —
   готовый детектор с подходящей лицензией: RT-DETRv2 / D-FINE / DEIM /
   RF-DETR (Apache-2.0) или YOLOX (Apache-2.0). **Ultralytics YOLO не брать:
   AGPL-3.0 несовместима с Apache-2.0 проекта.**
2. **Читатель плашки** — кроп 128×24 в полном разрешении: регрессия долей
   ХП/ресурса (или классификация по столбцам пикселей), уровень (18 классов),
   команда, щит, флаг «перекрыта/обрезана». Маленькая CNN, ~0.1 М параметров.
3. **Имя над плашкой** — кроп текста → классификатор по закрытому словарю
   имён (≈172) или CTC; для другого канала — ник (сопоставляется с
   составом).
4. **Облик чемпиона** — кроп тела 128×128 → эмбеддинг (метрическое обучение,
   ArcFace-подобная голова); ответ — ближайший из десяти в составе матча
   (состав из HUD/табло/Live API или накапливается по уверенным кадрам).
   Скины — просто разные примеры одного класса; редкие скины покрывает
   метрическое обучение лучше, чем 172-классовый softmax.
5. **Миньоны/монстры/варды** — класс прямо из детектора (классов мало),
   тип монстра уточняется по положению на карте (лагеря неподвижны).

### 3.3. Реальное время на RTX 5060 Ti (оценки, не замер)

| Этап | Оценка, мс | Основание |
|---|---:|---|
| Подготовка кадра на GPU (уже есть для камеры) | 1–2 | `patch_infer.py`, CUDA graphs |
| Детектор 960×544, ~10 М параметров, fp16 | 3–6 | патч-CNN 432×272 — 0.9 мс в CUDA graph; детектор в ~4× больше по пикселям и параметрам |
| Кропы + головы (до ~40 юнитов, батч) | 1–2 | маленькие CNN |
| Модель камеры | ~6 | README |
| Итого | 11–16 | ≥60 кадров/с при 1080p |

Обучение: детектор на ~20–50 тыс. кадров — часы на одной 5060 Ti; памяти 16 ГБ
хватает с запасом. Учитывать, что на машине идут другие расчёты.

## 4. Объединение с моделью камеры

### 4.1. Общий энкодер или раздельно

**Раздельно**, с общим конвейером:

* модель камеры видит вид сверху 6 ед./px (холст 432×272): плашка
  чемпиона там ~29×3 px, миньон ~12 px, текст не читается — общий энкодер
  пришлось бы учить на другом разрешении, и камера потеряла бы свою
  нормировку «пиксель = 6 ед.», на которой держится её устойчивость к HUD;
* модели развиваются с разной скоростью; общий энкодер связал бы их
  переобучение;
* общее — декодированный кадр на GPU, маска HUD, голова «не игра» (кадры
  «не игра» не идут в детектор), формат вывода.

Позже, когда обе модели устоятся, можно проверить общий ствол в полном
разрешении с двумя головами (камера получит больше деталей, детектор —
контекст карты). Не раньше, чем будет с чем сравнивать.

### 4.2. Экран → карта

Нужны две вещи: где камера (модель 1) и как экран ложится на землю
(геометрия).

**Геометрия.** Replay API даёт камеру целиком: глаз на высоте 1911.8 над
y=0, тангаж 56°, рыскание 0, FOV 40 (`data/replay/rand300/frames.csv`).
Проверка (разовый скрипт): 24 пары кадров одного момента с камерами в
пределах 700×400 ед., сдвиг картинки шаблоном в центре кадра против сдвига
камеры по API.

| | px на ед., горизонталь | px на ед., вертикаль | отношение |
|---|---:|---:|---:|
| замер по Replay API | 0.685 | 0.570 | 0.832 |
| пинхол, вертикальный FOV 40°, земля y=0 | 0.643 | 0.533 | 0.829 (= sin 56°) |
| `projection.json` в центре кадра | 0.644 | ~0.49 | — |

* Отношение осей совпало с sin 56° — тангаж верный. Абсолютный масштаб на
  6.5% больше пинхола: либо эффективное фокусное ~1580 px вместо 1484, либо
  земля под камерой на ~115 ед. выше нуля (дистанция меньше). Различить
  можно по кадрам над рекой (она ниже) — шаг 0.
* `projection.json` против эталона: ×0.94 по x и ×0.86 по y — та же ошибка
  масштаба, что #753 нашёл по меткам (0.906 и 0.847; там наклон по всему
  кадру, здесь — в центре). Источник — подбор гомографии по шумным меткам
  (label-noise.md, «Гомография»).
* **Решение:** заменить `projection.json` аналитической проекцией камеры
  (пинхол с тангажем 56° + два параметра — фокусное и высота земли),
  подогнанной по кадрам Replay API и известным точкам (башни). Для юнитов
  важна и высота рельефа: река ниже лайнов, ошибка ~5–8% расстояния от
  центра без неё (оценка). Модель 1 училась в старой системе — её ответ
  переводится поправкой (матрица 0.906/0.847 и сдвиг 3.5 px ≈ 205 ед. между
  центром рамки и точкой земли, replay-api.md) либо модель переучивается на
  новой геометрии.

**Точка юнита.** На землю проецируется точка основания тела (центр тени /
нижней кромки маски), а не плашка: высота плашки над моделью у чемпионов
разная (и меняется — Cho'Gath). Связь «плашка → основание» по чемпиону
выучивается на данных пути A.

**Ошибка на карте** (оценка): камера ~30 ед. (медиана модели 1) + точка
основания ~10–20 px ≈ 15–30 ед. + геометрия после замены единицы ед. → ~50
ед. медиана. Сверка на роликах — с иконками миникарты (~58 ед./px), на
реплее — с позициями из шага 0.

### 4.3. Формат «состояния игры» на кадр

Один JSON-объект на кадр (JSONL на ролик), плоский, со схемой версий. Пример:

```json
{"schema": "lol-state/1", "video": "58w57eJ5Qks", "t_video": 300.0,
 "game_time": 310, "is_game": 0.99,
 "camera": {"x": 6120, "z": 8410, "spread": 34, "agree": 0.82,
            "source": "patch-cnn-split16-notgame"},
 "geometry": "replay-pinhole/1",
 "units": [
   {"id": "champ:Irelia", "kind": "champion", "name": "Irelia", "name_p": 0.98,
    "team": "blue", "box": [1001, 360, 1140, 520], "foot": [1068, 515],
    "map": {"x": 6240, "z": 8180, "err": 50},
    "hp": 0.65, "hp_max": 1480, "res": 0.55, "res_type": "mana",
    "shield": 0.0, "level": 5, "bar_occluded": false, "track": 3},
   {"id": "minion:17", "kind": "minion", "sub": "caster", "team": "red",
    "box": [1040, 200, 1100, 250], "hp": 0.4, "track": 17}
 ],
 "roster": {"blue": ["Irelia", "..."], "red": ["Volibear", "..."]}}
```

Правила: координаты и на экране (всегда), и на карте (если камера
уверенная); имя геометрии в каждой строке, иначе файлы с разной
калибровкой нельзя сравнить; отсутствие записывается (чемпион из состава
вне кадра — `"visible": false` с последним известным местом), как у
spectral-sight.

### 4.4. Трекинг во времени

* **Чемпионы:** личность известна (имя/облик, ровно 10 на матч) — это не
  общий MOT, а фильтр на каждого: Калман в координатах карты + ограничения
  (скорость ≤ ~1000 ед./с без рывков, уровень только растёт, ХП меняется
  плавно, кроме смерти/возрождения у фонтана).
* **Миньоны, варды:** ByteTrack/OC-SORT (MIT) на экранных рамках с
  компенсацией движения камеры (сдвиг кадра = сдвиг камеры из модели 1).
* При 1 кадре/с (датасет) трекинг миньонов слабый; в live-режиме кадров
  больше — там он и нужен.
* Временная модель поверх эмбеддингов (патч-эмбеддинги камеры + эмбеддинги
  юнитов) — потом, после пофреймовой базы.

## 5. Этапы

Каждый этап заканчивается проверяемым результатом; дальше не идём, пока
результат не получен.

| # | Этап | Результат и как проверить | Срок (оценка) |
|---|---|---|---|
| 0 | **Разведка Replay API** (нужен пользователь) — сделано, итоги в [replay-render.md](replay-render.md) | `docs/replay-render.md`: таблица «флаг → что пропало» по снимкам; карта шума двух одинаковых снимков на паузе; работает ли `selectionName`+`cameraAttached` (позиция = юнит); отдаёт ли Live Client Data API в реплее состав и `skinID`; время на снимок; как включить имена чемпионов над плашками; подгонка геометрии (фокусное/высота земли, кадры над рекой и у башен) | 0.5–1 день |
| 1 | **Классический читатель плашек на роликах** | на 6 матчах `dataset/videos/`: полноту детекции плашек чемпионов против числа живых чемпионов в кадре по HUD (≥95%), точность имени (≥98% на читаемых), уровня (сверка с HUD), ХП (MAE доли против боковой панели HUD ≤3%); выход — псевдо-метки и JSONL состояния | 2–3 дня |
| 2 | **Сбор по Replay API** (`tools/replay_entities.py`) | 20 игр текущего патча × ~300 точек у чемпионов и волн; маски, плашки, ХП, состав; 50 случайных точек проверены глазами на странице просмотра (ошибки маски/класса < 2%) | 3–5 дней + ~3 ч работы ПК |
| 3 | **MVP-модель: детектор + читатель плашки** | на отложенных играх реплея: AP50 плашек чемпионов ≥0.95, миньонов ≥0.9; MAE ХП ≤2% (без перекрытий); уровень ≥98%; на роликах — против псевдо-меток этапа 1 и 200 кадров, проверенных вручную; скорость ≤8 мс на 1080p | 3–5 дней |
| 4 | **Облик чемпиона и имя** | классификатор облика: точность среди состава из 10 ≥97% на кадрах, где плашка видна (метка из имени), и на кадрах с закрытой плашкой (проверка глазами 200 шт.); top-1 среди всех ~172 — как справочная цифра | 3–4 дня |
| 5 | **Экран → карта, формат состояния** | аналитическая геометрия вместо `projection.json`; медиана ошибки позиции чемпиона на реплеях (эталон из шага 0) и против иконок миникарты на роликах; JSONL состояния на ролик; показ в веб-просмотрщике (точки юнитов на карте рядом с миникартой) | 2–3 дня |
| 6 | **Полный набор классов** | монстры (тип по лагерю), строения, варды, питомцы/клоны; AP50 по классам; ХП строений | 3–5 дней |
| 7 | **Трекинг и live** | IDF1/HOTA чемпионов и миньонов на коротких отрезках реплея (эталон — путь A через каждые 0.5 с); live-режим с юнитами, полный путь ≤16 мс | 4–6 дней |
| 8 | **Перенос** | другой канал (ник над плашкой), вид игрока (зелёная своя плашка, другой HUD), другой зум; без переобучения и после дообучения | по результатам |

MVP = этапы 0–3 (+5 для карты): чемпионы и миньоны с командой, ХП, уровнем
и местом на карте, ~2.5 недели.

### Метрики

* Детекция: AP50 и полнота по классам; для чемпионов — отдельно «плашка
  видна» / «плашка закрыта или вне кадра».
* Личность: точность среди состава; top-1/top-5 среди всех чемпионов.
* ХП/ресурс: MAE доли; доля ответов с ошибкой >5%. Уровень: точность.
* Карта: медиана, p90 ошибки в единицах игры (как у камеры).
* Трекинг: IDF1, число смен личности на минуту.
* Скорость: мс на кадр по стадиям (`bench_models.py`).
* Сплит — по матчам, как у модели камеры; реплеи и ролики не смешиваются в
  одном матче.

### Что нужно от пользователя

1. Шаг 0: открыть любой реплей текущего патча (Replay API уже включён),
   ~1 час не трогать ПК, пока скрипт снимает варианты рендера. Включить
   в настройках имена чемпионов над плашками (если в реплее это отдельная
   опция) и графику как у канала.
2. Шаг 2: клиент запущен и вход выполнен (скрипт сам скачает реплеи через
   LCU), ~3 часа ПК свободен с окном игры на переднем плане (до перехода на
   Windows Graphics Capture). Повторять раз в патч, если нужны свежие данные.
3. Глазами — проверить ~50 кадров разметки (страница просмотра) и ~200 кадров
   роликов на этапе 3–4 (по полчаса).

  replay-api.md); геометрия плашек в реплее при тех же настройках та же.
* Флаги рендера делают то, что следует из имени; на паузе кадр неподвижен
  (кроме шейдеров воды/травы). Проверяется на шаге 0.
* `/lol-replays/v1/rofls/{gameId}/download/graceful` по-прежнему скачивает
  чужие матчи текущего патча (видно по коду pyLoL, сам не запускал).
* Число чемпионов ≈172 (170 на 15.13 по pyLoL, +1–3 в год); скинов — по
  оценке 1800+.
* Оценки скорости детектора — по аналогии с патч-CNN, не замер.
* Размеры плашек и юнитов (118 px, 150 px и т. д.) — по одному кадру и README
  spectral-sight.
* Лицензии кода: брать только Apache-2.0/MIT/BSD; GPL/AGPL и репозитории без
  лицензии — только идеи и факты.
