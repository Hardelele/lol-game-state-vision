# Офлайн-прогон ролика: /state по кадрам, сети пачками (#843)

Набору данных для модели решений сильных игроков нужен снимок `/state`
(`state_service.build_snapshot`) на каждую секунду ролика — тот же, что coach
получает в игре. Live проходит кадр за кадром; здесь сети считают пачку
кадров на видеокарте, а логика с состоянием идёт по готовым выходам строго по
порядку кадров — тем же кодом `live.Session._step` / `_emit`, без копии.

Код:

* `lolstream/extract.py` — `OfflineSession` (сеанс live, которому кадры
  подаёт `process`), `BatchPre` (чистый счёт пачки), `Profiler` (время по
  стадиям), `Roster` (состав снаружи), `prefetch` (чтение в своём потоке);
* `lolstream/hud_pool.py` — полоса HUD в отдельных процессах;
* `lolstream/limits.py` — приоритет BelowNormal и не больше 4 потоков;
* `tools/extract_states.py` — командная строка;
* `tests/test_extract_states.py` — без сети и видеокарты.

## Запуск

```
python tools/extract_states.py D:/Videos/lol-coach/game.mp4 --fps 1 --batch 16 \
    --out D:/bc-data/states/game.jsonl.gz --roster roster.json
python tools/extract_states.py https://www.youtube.com/watch?v=XXXX --out x.jsonl.gz
```

Запись на кадр — строка JSON:

```
{"video_t": 17.0, "game_t": 689.5, "frame": 17, "state": {... снимок /state ...}}
```

`video_t` — секунды от начала ролика (ровно момент кадра, см. «Выравнивание
кадра»), `game_t` — время матча по полосе HUD (или null: полоса ещё не
подтверждена, не вид игрока, Tab), `state` — снимок схемы docs/state-api.md,
давности в нём — по ролику, а не по тому, как быстро шла видеокарта. С
`--keep-row` — ещё строка кадра live (`row`: камера, юниты, треки, события
трекера, добивания, окно размена). Рядом — `<out>.meta.json`: источник,
стадии, скорость, время пакетного счёта по стадиям, сколько кадров посчитано
мимо пачки (`misses`).

Флаги: `--stages` (по умолчанию `scene,camera,minimap,hud`; `default,+units`,
`all,-names`), `--batch` (16; 1 — обычный последовательный путь live),
`--fps` (1), `--start` / `--duration`, `--roster`, `--decode` (auto: NVDEC,
если ffmpeg его умеет), `--align` (exact), `--limit-rate` (2M), `--threads`
(4), `--hud-procs` (2), `--normal-priority`, `--profile` (только с
`--batch 1`).

### Стадии

| стадия | что | по умолчанию |
|---|---|---|
| scene | тип сцены (игра / Tab / магазин / клиент / …) | да |
| camera | модель камеры (центр камеры, «не игра» по патчам) | да |
| minimap | иконки миникарты: места и видимость всех, состав и вид по HUD | да |
| hud | свой HUD: Q/W/E/R и D/F, CS и часы матча | да |
| units | юниты на экране, трекер, добивания, окно размена, ХП на экране | нет |
| names | имена над чемпионами (нужен units; банка имён на этой машине нет) | нет |

Без minimap нет вида (он решается по HUD), а без вида HUD своего игрока не
читается (паспорт). Без scene всё считается игрой.

### Что есть в снимке без Live Client API

У ролика API нет, поэтому `me.level`, золото, предметы, счёт, `relation`,
роль, руны — отказ с причиной. Читателя уровня и ХП своего HUD в проекте нет:
ХП в снимке — только с полоски над чемпионом (стадия units), уровень — только
из API. Жив / мёртв на виде игрока не наблюдается (панелей наблюдателя нет,
API нет) — `alive` отказ. Это ограничения набора, а не офлайн-прогона: live
на ролике отдаёт то же.

### Состав (`--roster`)

На виде игрока состав по портретам не принимается (паспорт, #786), и без
состава иконки миникарты не назначаются: снимок без мест чемпионов. `--roster`
задаёт состав снаружи:

```
{"ORDER": ["Urgot", "Briar", "Heimerdinger", "Jinx", "Lux"],
 "CHAOS": ["Volibear", "Rammus", "Yone", "MissFortune", "Lulu"], "me": "Volibear"}
```

Свой чемпион обязателен: на миникарте вида игрока синие — своя команда.
Состав идёт только в назначение иконок (`LiveChampions.set_api`) и только
когда вид решён как вид игрока; в паспорте источник состава — `manual`. В
MatchState он не попадает, поэтому в снимке `champions` — источник `hud`, а
факты API (уровень, время по API, смерти) не выдумываются. У наблюдателя
состав читается по портретам, `--roster` не нужен. Для своих записей состав
берётся из `data/loadouts/<день>.jsonl` (игра — по `game_start`).

## Как устроено

`OfflineSession` — `live.Session` без своего потока: `process` открывает
источник, строит путь кадра (`build_pipeline`) и подаёт кадры в `_step`.
Отличия от live, все ради воспроизводимости:

* часы модуля live подменены временем кадра (`_Clock`) — давности в снимке
  по ролику;
* чтение состава по портретам — в потоке кадра, а не в своём: в live его итог
  приходит в случайный кадр;
* картинки для смотрелки не сжимаются, уменьшенный кадр целиком не строится;
* снимок строится сразу после выдачи кадра (`_store`).

`BatchPre` на пачку кадров считает чистый инференс: тип сцены, модель камеры
(подготовка кадра, сеть и сведение голосов — как `FramePrep` и
`PatchInfer._post`, только для пачки), иконки миникарты (`IconModel` пачкой),
детектор юнитов (подготовка, fp16, decode). Чистые функции кадра на
процессоре — миникарта 256×256 (LANCZOS), её белая маска, рамка
(`find_box_clipped`) — в пуле потоков, полоса HUD (~20 мс на кадр: ближайший
сосед по 3183 образцам цифр) — в процессах `hud_pool`. Пачка n+1 считается в
своём потоке, пока по порядку идёт логика пачки n.

Выходы подставляются в путь кадра заместителями моделей. Вход иконок и юнитов
зависит от состояния (прямоугольник миникарты, маска вида), поэтому пачка
считается по состоянию на свой запуск, а заместитель сверяет: миникарта — по
месту кадра в памяти и прямоугольнику, иконки и маска — по содержимому
миникарты, юниты — по маске вида, полоса HUD — по содержимому выреза. Не
совпало (нашли миникарту, решился вид посреди пачки) — кадр считается обычной
моделью, счётчик `misses`. Поэтому пакетный путь отличается от
последовательного только числами пакетного счёта сетей.

## Выравнивание кадра

Фильтр `fps` ffmpeg по умолчанию оставляет в каждом интервале последний кадр
перед его серединой: кадр с меткой `t` у ролика 60 к/с показывает момент
t + 0.48 с при 1 к/с и t + 0.23 с при 2 к/с (замер по пикселям против
распаковки всех 60 кадров). Так работает live у роликов — метки времени
опаздывают на полкадра, а прогоны 1 и 2 к/с видят разные кадры. Экстрактор по
умолчанию берёт кадр ровно в момент метки (`--align exact`, `round=up`):
1 к/с — подмножество кадров 2 к/с. `--align near` — как в live. Свой экран
(live на 2 к/с) снимается по такту и этой поправки не касается.

## Разложение пути кадра live

`--profile` (обёртки с синхронизацией видеокарты), последовательный путь со
всеми стадиями и картинками для смотрелки — как live; ролик 1080p60 H.264
(2026-10-14 Volibear, 300–390 с), 2 к/с, 180 кадров, днём на свободной машине,
4 потока. Время включает вложенные вызовы; мс на кадр:

| стадия | мс |
|---|---|
| весь `_step` (без ожидания кадра) | **61.4** |
| полоса HUD: CS и часы (`_stats_step`, ближайший сосед по цифрам) | 19.5 |
| панель умений Q/W/E/R и D/F (`_spells_step`) | 5.6 |
| сжатие картинок для смотрелки + кадр целиком 640×360 (`_store`, только live) | 5.1 (JPEG 1.8, уменьшение 1.4) |
| белая маска миникарты (`white_mask`) | 4.2 |
| иконки миникарты: сеть 2.75 + назначение и панели 0.1 | 2.9 |
| модель камеры: подготовка 1.3 + сеть и сведение голосов 2.85 | 4.1 |
| свои / враги по полоскам (`assign_sides`, units) | 2.8 |
| детектор юнитов (units) | 2.7 |
| тип сцены (сеть) | 2.4 |
| рамка на миникарте (`find_box_clipped`, истина камеры) | 1.9 |
| вырез миникарты 256×256 (LANCZOS) | 1.7 |
| поиск миникарты (`_minimap_step`) | 0.7 |
| снимок /state (`build_snapshot` 0.6 + входы 0.2) | 0.8 |
| состав по портретам (раз в 5 с потока) | 0.4 |
| трекер юнитов | 0.4 |
| прочее (загрузка кадра в видеопамять, паспорт, MatchState, добивания, окно) | ~7 |

Ожидание кадра от ffmpeg при 2 к/с — медиана 4.4 мс (ffmpeg распаковывает
впереди, параллельно); сама распаковка NVDEC — 32 мс на секунду ролика 60 к/с
(~31× реального времени, замер распаковки без сетей). Итого сети — ~15 мс
из 61, остальное — процессор, и треть всего пути — полоса HUD. Цифры «~95 мс»
из прежних замеров live этим прогоном не воспроизводились: на ролике
последовательный путь — 61 мс плюс ожидание кадра; на своём экране к нему
добавляется захват и опрос API (не мерялись).

Наблюдение по ходу: при 16 потоках BLAS (по умолчанию) и занятой машине чтение
состава по портретам занимало 3–7 с вместо 0.4 мс — переподписка потоков.
Отсюда скромный режим по умолчанию.

## Эквивалентность пакетного пути

Три ролика своей записи (вид игрока, Ущелье, 1080p60), по 10 минут, 1 к/с,
`--align exact`, стадии по умолчанию, состав `--roster` из data/loadouts:
2026-10-14 Volibear (0–600 с), 2026-10-14 Ekko (600–1200 с), 2026-10-13
Volibear (300–900 с). Пакетный путь (batch 16) против последовательного
(batch 1) на тех же кадрах; место — совпадение в пределах 0.003 доли
миникарты (~44 ед.), часы — 0.05 с:

| поле | совпало | расхождений | известно |
|---|---|---|---|
| место своего (`position`) | 0.9994 | 1 из 1746 | 1.00 |
| место остальных | 0.9999 | 2 из 15714 | 0.99 |
| зона места (`place`) | 0.9999 | 1 из 15714 | 0.99 |
| видимость (`map_state`) | 1.0000 | 0 | 1.00 |
| часы матча | 1.0000 | 0 из 1800 | 0.96 |
| CS | 1.0000 | 0 из 1800 | 0.97 |
| Q/W/E/R | 1.0000 | 0 из 7200 | 0.69 |
| D/F | 1.0000 | 0 из 3600 | 0.86 |
| тип сцены, вид, число чемпионов | 1.0000 | 0 | 1.00 |
| жив / мёртв, ХП | 1.0000 | 0 | 0.00 (не наблюдаются, см. выше) |

Расхождения — только числа: иконки миникарты пачкой (`IconModel`) и по одной
(`IconGraph`, CUDA graph) дают координаты, отличающиеся в последнем знаке
(медиана 1e-4 доли миникарты, ~1 ед. карты), и на трёх кадрах из 1800 одна
иконка ушла на 0.004–0.014 доли (до ~200 ед.: другой пик детектора). Снимки
целиком (без давностей и паспорта) побитово совпали в 27–45% кадров —
остальные отличаются этим последним знаком мест и центра камеры. Со стадией
units (тот же 2026-10-14 Volibear): 131 / 131 смерть крипов в трекере,
173 / 174 новых трека, добивания и окна размена — те же, место — 1 из 5238.

Кадров, посчитанных мимо пачки (`misses`), — 14–16 у иконок за прогон (пачка,
в которой нашли миникарту) и 15 у юнитов (пачка, в которой решился вид).

## 1 к/с против 2 к/с

Тот же последовательный путь при 1 и 2 к/с, сравнение на общих моментах (при
`--align exact` это один и тот же кадр ролика), три ролика по 10 минут:

| поле | совпало | что меняется |
|---|---|---|
| место видимого сейчас (`map_state` visible) | 1.0000 | ничего: кадр тот же |
| место «Видели» (`remembered`) | 0.62–0.74 | при 2 к/с последний раз видели на промежуточном кадре; давность — медиана 11.5 / 10.5 с (−1 с) |
| зона места | 0.98 | следствие прошлой строки |
| видимость | 0.997 | в основном первые секунды (прогрев); у Ekko 13 раз «не видели» → «Видели» (видели на промежуточном кадре) |
| часы матча | 0.26 | при 1 к/с на 0.25 с раньше, постоянно (у 2 из 3 роликов на каждом кадре, у Ekko в среднем 0.07 с): полоса показывает целые секунды, и при одной фазе чтений отрезок `HudClock` не сужается |
| CS | 0.949 | при 1 к/с ниже в 4–6% кадров: подтверждение двумя прочтениями — 1 с вместо 0.5 с |
| Q/W/E/R, D/F | 0.997–0.998 | в основном прогрев (эталон готовой иконки набирается по времени, REF_EVERY 2 с), единичные кадры позже |

Поля трекера и окон (стадия units, 2026-10-14 Volibear, 10 мин):

| за минуту | 1 к/с | 2 к/с |
|---|---|---|
| смерти крипов (`unit_death`) | 13.1 | 19.0 (+45%) |
| новые треки | 17.4 | 23.0 |
| треков «не видно» на кадр | 7.4 | 8.6 |
| добил (`last_hit`) | 3.0 | 2.7 |
| не добил (`missed_last_hit`) | 1.3 | 3.0 |
| рост CS без смерти в кадре (`cs_unseen`) | 2.5 | 3.4 |
| окно размена (`trade_window`) | 1.1 | 3.6 (×3.3) |
| нажатия умений (`ability_cast`) | 2.5 | 2.9 |

Почему: пороги заданы в кадрах, а не в секундах. Трекер — `CONFIRM = 2` пары
подряд для нового трека и `MISS_IN_VIEW = 3` кадра для потери (1.5 с при
2 к/с и 3 с при 1 к/с), смерть по тренду ХП — экстраполяция ХП к кадру
пропажи по скорости между кадрами (при 1 к/с миньон за секунду успевает
умереть и потеряться без «тренда»); MatchState — `dead_n < 2` кадров «мёртв»
без таймера, `ROSTER_SWITCH = 3` кадра; окно размена — по паре соседних
прочтений «готово → перезарядка» (`GAP = 1.5` с) и по ХП миньона на
добивание на текущем кадре. Временные пороги (`LEAD 2.5 с`, `ROSTER_EVERY`,
`REF_EVERY`, `CLOCK_STALE`) от частоты почти не зависят.

### Как держать набор и live согласованными

1. Модель решений учить и кормить на одной частоте: live на 2 к/с пишет для
   модели снимок на каждом втором кадре (целые секунды потока, `exact`), но
   логика с состоянием идёт на 2 к/с — тогда признаки трекера и окон в наборе
   надо считать тоже на 2 к/с (`--fps 2`, ~1.7× дольше). Самый честный путь.
2. Или перевести пороги в кадрах на секунды (`MISS_IN_VIEW`, `CONFIRM`,
   `dead_n`, `ROSTER_SWITCH`) и экстраполяцию ХП — на время между кадрами:
   тогда 1 и 2 к/с сходятся по смыслу, а набор можно гнать на 1 к/с. Это
   правка логики live, отдельная задача.
3. Признаки модели брать по окну времени, а не по кадрам: «смертей крипов за
   10 с», «последнее место не старше N с», а не «за 10 кадров»; для мест —
   только видимые сейчас и давность «Видели» (она сопоставима, −1 с).
4. Часы — `game_t` с поправкой: при одной фазе чтений отрезок HudClock шире
   (±0.5 с); для решений модели это несущественно, но при сравнении с API —
   допуск 0.5 с.
5. Метки времени live у роликов (`near`) опаздывают на 0.5 / fps: при сшивке
   набора с live-журналами ролика добавлять 0.5 / fps или включить `exact` в
   live (правка `VideoSource` в live — не сделана).

## Скорость

Ролик 2026-10-14 Volibear, 1080p60 H.264 15 Мбит/с, 4 минуты (300–540 с),
1 к/с, стадии по умолчанию, 4 потока, полоса HUD в 2 процессах. «Устойчиво» —
мс на кадр после первой четверти (без загрузки моделей и промотки начала).
Два замера: днём на свободной машине (код до перекрытия пачек) и ночью в тихом
режиме (процессор ограничен 60%, итоговый код):

| batch | днём, мс/кадр | ночью, мс/кадр | VRAM процесса (reserved) | GPU, % | NVDEC, % |
|---|---|---|---|---|---|
| 1 | 61.2 | 85.6 | 0.3 ГБ | 19–32 | 54–66 |
| 8 | 35.7 | 37.9 | 0.6 ГБ | 13–30 | 48–72 |
| 16 | 38.1 | 38.0 | 0.9 ГБ | 12–29 | 47–69 |
| 32 | 40.4 | 45.1 | 1.8 ГБ | 10–29 | 38–69 |
| 64 | 35.3 | 47.2 | 3.5 ГБ | 9–28 | 39–71 |

Одна распаковка без сетей — 32.1 мс на секунду ролика (NVDEC ~31×
реального времени). Узкое место — распаковка: при batch 8–16 путь в пределах
~15% от неё, видеокарта занята на 10–30%. Сверх 16 пачка не ускоряет (ночью
даже медленнее: дольше ждать процессорную часть пачки), а миникарта, найденная
посреди большой пачки, даёт больше кадров мимо неё.

Итог при batch 8–16: ~38 мс на секунду ролика при 1 к/с — **2.3 с на минуту
игры, ~70 с на 30-минутный ролик** плюс ~5 с на загрузку моделей (оценка: время
до первой записи минус промотка начала) — около 1.3 минуты на ролик.
Последовательный путь (batch 1) — 1.8–2.6 минуты на тот же ролик. 2 к/с при
batch 1 — в 1.7–1.9 раза дольше, чем 1 к/с (10 минут ролика: 82 / 44 с,
117 / 69 с, 100 / 61 с; ночью, между прогонами пилота — замеры не чистые).

Сколько прогонов параллельно: NVDEC один на карту и насыщается на ~41 секунде
ролика в секунду на все процессы вместе (замер: 1 ffmpeg — 37.7×, 2 — 40.6×,
3–4 — 41.4×; распаковка на процессоре в 4 потока — ~5× и душит машину).
Один прогон уже берёт 60–70% NVDEC, поэтому второй параллельный прибавит не
больше ~30% общей скорости; по видеопамяти (≈1.4 ГБ на прогон при batch 16 с
контекстом CUDA) влезло бы с десяток. Рамки владельца — один тяжёлый прогон
за раз; больше одного смысла и не имеет.

## Ограничения

* Без Live Client API: уровень, золото, предметы, жив / мёртв на виде игрока —
  отказ с причиной; ХП — только со стадией units (полоска над чемпионом), не с
  HUD; читателей уровня и ХП своего HUD в проекте нет.
* Вид игрока без `--roster` — без мест чемпионов (состав по портретам там не
  принимается).
* Пакетный путь совпадает с последовательным по смыслу, но не побитово:
  числа сетей пачкой отличаются в последнем знаке (см. «Эквивалентность»).
* Отличия от live, кроме пачек: часы — по ролику, состав читается в потоке
  кадра, кадр по умолчанию — `exact` (live — `near`).
* Скорость упирается в NVDEC; распаковка «только нужных кадров» у H.264 с
  B-кадрами невозможна (опорные кадры всё равно распаковываются; `-skip_frame
  noref` у NVDEC дал 5% и меняет выбор кадра), ключевые кадры OBS — не каждую
  секунду.
* Ссылка YouTube: потолок полосы yt-dlp 2 МБ/с по умолчанию (всплеск трафика
  выбивает из онлайн-игры) — по оценке (битрейт 1080p60 YouTube ~1–1.5 МБ/с,
  не мерялся) ~1.3–2× реального времени, то есть
  по ссылке прогон упирается в полосу, а не в распаковку. Перемотки по ссылке
  нет (как и в live). Чтение по ссылке в этой задаче не проверялось: ролики
  брались с диска.
* Банка имён (`runs/identity/names.npz`) на этой машине нет — стадия names
  ничего не читает.
* Замеры скорости — на одном ролике и одной машине, часть — при работе
  других прогонов и в тихом режиме; эквивалентность — на трёх своих роликах
  вида игрока; роликов наблюдателя и чужих роликов не было
  (D:/bc-data/video в начале работы был пуст, ролики пилота появились позже и
  шли в его прогонах — их не брал).
