# Экран как источник кадров (#794)

Задача 1A из [mvp-state-service.md](mvp-state-service.md): live читает не
только ролик YouTube, но и собственный экран игрока. Код —
`lolstream/frame_source.py`, тесты — `tests/test_frame_source.py`, замер
снимка — `tools/bench_screen.py`.

## Интерфейс

Сеанс live видит только `FrameSource`:

| Член | Что |
| --- | --- |
| `kind` | `youtube` / `file` / `screen` |
| `fps` | сколько кадров в секунду просят |
| `backend`, `backend_note` | чем снимаются кадры и почему (`ffmpeg`; `dxcam: основной бэкенд`; `mss: запасной — dxcam: …`) |
| `size` | ожидаемый (W, H) до первого кадра — под него собирается путь кадра |
| `open()` | ролик — `probe_url` / `probe`; экран — окна и бэкенд захвата (звать в потоке, который читает: mss привязан к потоку) |
| `read() -> Frame` | следующий кадр или его отсутствие с причиной |
| `close()` | погасить ffmpeg / yt-dlp или освободить захват |
| `describe() -> dict` | всё перечисленное — для `status()` сеанса и паспорта трансляции (2C) |

`Frame`: `status` (`Status`), `t` (с), `image` (RGB uint8 (H, W, 3) или
`None`), `reason` (почему кадра нет), `ok`, `size`.

| `Status` | Когда |
| --- | --- |
| `OK` | кадр есть |
| `PAUSED` | окно игры не в фокусе: поверх другое окно, снимать нечего |
| `MINIMIZED` | окно свёрнуто |
| `NO_WINDOW` | окна `League of Legends (TM) Client` нет (игра не запущена или закрылась) |
| `NO_FRAME` | снимок не удался: сбой бэкенда, окно за пределами области захвата, нового кадра ещё нет |
| `ENDED` | ролик кончился (`ролик кончился` или `поток кончился: поток оборван: …`) или источник закрыт |

Отказ — состояние, а не исключение: пауза в игре обычна, сеанс её
показывает и ждёт. Исключение — только когда источник открыть нельзя
вообще (ролик не найден, ни один бэкенд захвата не открылся).

## Экран

* Окно — по точному заголовку `League of Legends (TM) Client`
  (`FindWindowW`), прямоугольник — клиентская область (`GetClientRect` +
  `ClientToScreen`), без рамки и заголовка. Процесс переводится в режим
  per-monitor DPI v2, иначе при масштабе Windows не 100% прямоугольник
  не совпал бы с пикселями; если перевести не вышло — запись в `notes`.
* Пауза: окно не на переднем плане (`GetForegroundWindow`) или свёрнуто
  (`IsIconic`). Закрытое окно ищется заново на каждом такте.
* Бэкенд: `auto` — dxcam (DXGI Desktop Duplication), если не открылся —
  mss, и `backend_note` говорит почему. Явно заданный бэкенд не
  подменяется. Посреди сеанса бэкенд не меняется: сбой снимка — `NO_FRAME`
  с текстом ошибки.
* dxcam видит только основной монитор. Окно на втором мониторе — отказ
  `NO_FRAME` «выходит за область захвата», а не обрезанный кадр.
* Ограничение кадр/с: `read()` ждёт до следующего такта 1 / fps, в том
  числе для отказов (цикл сеанса не крутится вхолостую); опоздавший снимок
  не догоняется пачкой.
* Кадр не 1080p отдаётся как есть; к 1080p его приводит путь кадра (#788).
  `Frame.size` — размер именно этого кадра: окно могли растянуть.

## В сеансе live

`Session(sid, run, source, device, api=None, build=None)` читает только
`FrameSource`; `live.start(vid, …)` даёт ему `VideoSource` ролика,
`live.start_screen(run, fps, backend)` — `ScreenSource` (id сеанса
`screen`) и Live Client своей игры. В смотрелке — кнопка «свой экран ▶»,
маршрут `POST /api/live/start` с `{"source": "screen", "fps", "backend"}`.

* `open()` и все `read()` идут в потоке сеанса (mss привязан к потоку).
* Модели собирает `build_pipeline(size, run, device, fps) -> Pipeline` под
  размер кадра. Размер известен после `open()` (ролик, окно уже есть) —
  сборка до первого кадра, как раньше; нет (окна ещё нет) — на первом кадре.
* Время строки кадра — `Frame.t`, а не номер / fps.
* Кадра нет — строк нет, сеанс идёт; в `status()`:
  `source_state = {"state": "paused", "reason": "пауза: окно игры не в фокусе",
  "t": 12.5, "since": <unix-время смены состояния>, "size": null}` и счётчик
  отказов по причинам `source_gaps = {"paused": 25}`; `source` —
  `describe()` источника (бэкенд и почему).
* `ENDED` — конец сеанса (`state` «кончился»); причина обрыва ролика
  (`short_stream`) дописывается в `note`.
* Размер кадра сменился (окно растянули) — кадры прогрева старого размера
  отдаются, путь кадра собирается заново под новый размер, в `note` —
  «размер кадра 1920x1080 → 1600x900: путь кадра пересобран». Память матча
  (`MatchState`) переживает пересборку (проекция — новая), чемпионы
  (`LiveChampions`: прочитанный состав и раскладка) переходят в новый путь —
  они от размера кадра не зависят; трекер юнитов, поиск миникарты и прогрев
  рамки начинаются заново. Паспорт получает `set_frame_size` (миникарта —
  искать заново).
* Скорость к реальному времени (`speed`) у экрана — `null`: он идёт в
  реальном времени.
* Память кадров (#801). У ролика — потолок `MAX_FRAMES` (5400): дальше
  сеанс не читает, в `note` — «потолок памяти». Свой экран живёт через
  много игр подряд, и тот же потолок обрывал его посреди игры (при 2 кадр/с —
  через 45 минут от запуска сервиса, вместе с сервисом состояния для coach).
  У экрана вместо потолка — скользящее окно: последние `SCREEN_WINDOW`
  (5400, 45 минут при 2 кадр/с) кадров в `rows` и картинки к ним (`scene`,
  `mini`, `full`, `heat`); старые выбрасываются, их картинки отдают 404.
  Кадр в окне ~120 КБ (сцена ~37 КБ, кадр целиком ~43 КБ, миникарта ~18 КБ,
  тепловая карта 8 КБ, строка), окно — ~650 МБ, как прежний потолок.
  Номер кадра `i` — сквозной за сеанс. `status(since)` отдаёт кадры с
  номером `>= since`; `count` — номер следующего кадра (всего выдано, с
  выброшенными), его и передавать в `since` дальше; `window` — размер окна
  (у ролика `null`), `first` — номер старейшего кадра в памяти,
  `dropped_before` — сколько кадров из запрошенных (`since` … `first`) уже
  выброшено. Смотрелка держит то же окно. Хвостом держатся и события Live
  Client (`API_EVENTS_KEEP`, счёт всех — `api.events`), события контекста
  матча (`match_state.EVENTS_KEEP`) и ушедшие треки юнитов
  (`unit_tracker.GONE_KEEP`); на новой игре (событие `roster`) треки
  прошлой сбрасываются — у чемпионов срока нет, и они висели бы вечно.

### Миникарта своего экрана (#803)

Поиск миникарты (`lolvision/minimap_locate.Locator`) сначала сравнивает
угол кадра с эталоном Ущелья (градиенты содержимого карты). На Воющей
бездне (ARAM) эталон не находит ничего (совпадение 0.15 при пороге 0.40), а
миникарта игрока может быть увеличена, и прямоугольник раскладки режет не
то. Поэтому дальше:

* **рамка миникарты** (`locate_frame`): золотая линия и тёмная окантовка
  сверху и слева одинаковы на всех картах, а масштаб миникарты — одна
  настройка клиента. Перебирается масштаб, левый верхний угол — по прямой
  `ANCHOR` (миникарта привязана к правому нижнему углу; три замера 0.88 /
  1.00 / 1.205 — ошибка ≤ 0.7 px). Совпадение полосы рамки у нынешнего
  интерфейса 0.89–0.99, у старой рамки без золотой линии и не игры — не
  выше 0.62, порог 0.80. Кадр ARAM — ×1.2025, в пределах 0.4 px от
  прямоугольника, найденного эталоном на Ущелье у того же игрока; ~100 мс
  на попытку, только пока не найдена;
* **сохранённый прямоугольник**: найденный эталоном (`how = map`)
  прямоугольник своего экрана пишется в `%LOCALAPPDATA%/lolstream/
  minimap_fit.json` (по одному на размер кадра; не в data/, runs/,
  dataset/). На другой карте он берётся первым, если рамка на его месте;
  у ролика (`live.start`) файла нет — масштаб там чужой;
* **явный масштаб**: `python tools/live_screen.py --minimap-scale 1.2`
  (`live.start_screen(..., minimap_scale=1.2)`) — прямоугольник по прямой,
  без поиска, с первого кадра.

Как найдена — в `note` сеанса и в `passport.items.minimap.how`; `status()
.minimap.how` — `map` / `frame` / `saved` / `manual`. Сборка датасета
(`tools/build_coords.py`) рамку не использует: набор — Ущелье, и он
собирается как раньше. Что меняется в выходе на другой карте — раздел
«Карты, кроме Ущелья» в docs/state-api.md.

## Время снимка

```
python tools/bench_screen.py --n 300                 # окно игры, dxcam и mss
python tools/bench_screen.py --full --every 0.5      # весь монитор, с паузой как в live
python tools/bench_screen.py --fake 0.002            # проверка самого скрипта без экрана
```

Печатает на бэкенд медиану и p95 времени снимка (мс), сколько раз нового
кадра не было (у dxcam на статичном экране — мерить при движении) и что
снималось. Цифры: _ещё не сняты_ (снимает интегратор вместе с
пользователем, в комментарий #794).

## Просадка FPS игры

Цель — FPS игры без нашего процесса, с одним захватом и с полным live
(захват + модели на видеокарте). Предлагаемый способ:

1. **Сцена повторяемая.** Practice Tool, один и тот же чемпион и место
   (например, у своего фонтана, камера закреплена), без боя. Настройки
   графики и ограничение FPS игры — как обычно у пользователя, но
   записать их; лимит FPS в игре на время замера лучше снять («Без
   ограничений»), иначе просадка спрячется под потолком.
2. **Счётчик.** Основной — [PresentMon](https://github.com/GameTechDev/PresentMon)
   (Intel, открытый, читает ETW-события Present; на этой машине пока не
   установлен): `PresentMon --process_name "League of Legends.exe"
   --timed 60 --terminate_after_timed --output_file run.csv`, затем по
   `MsBetweenPresents` — средний FPS, 1% low (p99 времени кадра). Запасной —
   встроенный счётчик игры (Ctrl+F, FPS и пинг в углу) — только среднее на
   глаз, без 1% low; годится для грубой проверки.
3. **Прогоны** по 60 с, каждый 3 раза, в одном порядке с перерывом:
   * A — без нашего процесса;
   * B — только захват: `python tools/bench_screen.py --backend dxcam --every 0.5 --n 120`
     (затем то же для mss);
   * C — полный live по экрану на рабочем fps (смотрелка, «свой экран ▶»),
     с моделями на видеокарте.
4. **Итог** в комментарий #794: медиана FPS и 1% low по A/B/C, разница с A
   в процентах, fps сеанса, бэкенд, разрешение, видеокарта, версия драйвера.
   Отдельно — загрузка видеокарты (`nvidia-smi dmon -s u` на время прогона).

Не мерить во время ранкед-игры: замер — в Practice Tool, по договорённости
с пользователем.
