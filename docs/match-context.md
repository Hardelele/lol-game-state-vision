# Контекст матча (#780)

Главная задача модели — собирать состояние матча во времени, а не
отвечать по одному кадру. Модели кадра (тип сцены, камера, юниты,
миникарта, состав, жив ли, имена) всё забывают на следующем кадре; контекст
помнит, выводит и сверяет.

Код: `lolvision/match_state.py` (без сетей, только наблюдения), подключён в
`lolstream/live.py`; тесты `tests/test_match_state.py`.

## Этап 1: что уже ведётся

По каждому из десяти чемпионов:

| что | откуда | как хранится |
|---|---|---|
| где | миникарта (точно), основной вид — имя над плашкой + центр камеры + сдвиг от центра экрана (грубо, без перспективы) | значение, время, источник |
| виден сейчас / помним / мёртв / нет данных | всё вместе | состояние |
| жив / мёртв, момент возрождения | панели HUD (таймер → момент) | значение, время, источник |
| ХП | плашка на основном виде | значение, время |

События: `death` (кто, где видели последний раз, таймер), `respawn`
(источник: панель HUD, миникарта или вывод по таймеру), `roster` (новый
матч).

Правила игры — ограничения:

* состав не меняется в матче; другой состав три кадра подряд — новый матч;
* мёртвого не видно на миникарте и на экране (имя над плашкой мёртвого —
  ошибка чтения, не наблюдение);
* возрождение не раньше конца таймера (с запасом 2 с): панель под баннером
  объявления читается как «жив» посреди отсчёта — на 58w57eJ5Qks у Jinx и
  Lulu 349–351 с, у Zyra 830–837 с, отсчёт после этого продолжается;
  такие кадры — `conflicts`, сигнал для #781;
* смерть без таймера (одиночная ошибка чтения) — со второго кадра подряд;
* возрождается у своего фонтана — место выведено, а не увидено;
* кадры не «игра» (Tab, магазин…) наблюдений не дают, память остаётся.

## Что видно на 58w57eJ5Qks (15 мин потока, 1 кадр/с)

* 34 смерти и 31 возрождение; возрождения: 15 по панели, 13 по миникарте
  (иконка появилась у фонтана), 3 выведены по таймеру — панели в тот момент
  не было видно.
* Ложные пары «возродился — умер снова» от мигающей панели: были 4, после
  правила таймера 0.
* Из 8 860 записей «чемпион × кадр»: виден сейчас 66%, помним 28% (медиана
  возраста 7 с, p90 26 с), мёртв 6%, нет данных 0.8%.

Цена — доли миллисекунды на кадр (только Python над десятью записями).

## В смотрелке

* миникарта: кого сейчас не видно — там, где видели последний раз, с
  пунктирным кольцом и возрастом («12с»), тусклее со временем;
* состав: «не виден N с» в подсказке; если панель закрыта, а контекст знает,
  что чемпион мёртв, — серый портрет с таймером из контекста;
* строка «события»: последние смерти и возрождения до текущего кадра.

## Строка кадра

Записи строки — `lolvision/records.py`, именованные поля, версия формата —
`row["schema"]` (сейчас 1). `row["ctx"]` — по составу записи `ChampCtx`:
`name, team, state, u, v, age` (возраст места, с), `src` (источник места),
`hp, respawn_in` (до возрождения, с); `null` — значения нет. `row["ev"]` —
события этого кадра: `{"t", "type", …}`, `type` — `death` (`name, team, u, v,
respawn_in`), `respawn` (`name, team, src`), `roster` (`roster`).

## Постоянные id юнитов (#782)

Код: `lolvision/unit_tracker.py`, тесты `tests/test_unit_tracker.py`, в live —
`row["tracks"]` и `row["uev"]`.

* **Сопоставление на карте.** Точка кадра → смещение от центра камеры по
  гомографии `dataset/layouts/projection.json` (+ центр камеры — ответ
  модели камеры). На экране один крип между кадрами уезжает на сотни
  пикселей вместе с камерой, на карте — на свой шаг.
* Предсказание по скорости трека, венгерский алгоритм внутри (класс,
  команда), строб: базовая ошибка + максимальная скорость × прошедшее время;
  у миньона рост ХП штрафуется. Чемпион с прочитанным именем — именной id.
* Трек без пары: должен быть виден (место внутри зоны ответов детектора) и
  ХП было ≤ 30% — **умер** (`unit_death`); должен быть виден, но 3 кадра нет —
  **потерян**; вне кадра — **не виден**, живёт до срока (миньон 20 с,
  вард 3 мин) и при возвращении получает прежний id.
* id: `top-minion-…`, `mid-minion-…`, `jungle-minion-…` (линия — по месту
  рождения), `ward-…`, `champ-CHAOS-Volibear`. Новый экземпляр — новый id.

`row["tracks"]` — записи `TrackRec`: `id, kind, team, state, u, v, x, y, hp,
age`; состояние — seen / unseen / lost, `x, y` (доли кадра) — только у
видимого, иначе `null`; неподтверждённые (одна встреча) не выдаются.
`row["uev"]` — `unit_new` (`id, kind, team`) и `unit_death` (`id, kind, team,
u, v`).

Проверка на 58w57eJ5Qks (4 мин, 3 кадра/с): на плотной волне из 14 крипов
id держатся все 6 кадров подряд (2 с), пока камера двигается; за 4 мин —
119 треков миньонов (медиана жизни 7.7 с, 16 встреч), 70 смертей в кадре.
Настоящей метрики (подмены id, «умер» против «пропал») нет — нужна истина
Replay API (#774).

Ограничения:

* при 1 кадре/с миньон проходит ~325 ед. — больше шага в волне; для
  трекинга волн нужен поток 3+ кадр/с (смотрелка позволяет до 10);
* монстры и постройки детектор пока не находит — их id впереди (классы есть
  в ручном эталоне);
* тип миньона (ближний / дальний / осадный / супер) не различается;
* «кто добил» — не сделано.
